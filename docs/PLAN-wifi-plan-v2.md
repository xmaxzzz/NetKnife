# Wi-Fi план v2 — план работ (ждёт команды на запуск)

Статус: 2026-10-19 — пользователь выбрал «всё для ноутбука»: этапы 1, 2, 4 в работе; этап 3 (телефон) ОТМЕНЁН — браузер и iOS-приложение не получают RSSI/скан (NEHotspotHelper только для операторов), выгода не стоит Mac+Developer.

## Ограничение, на котором всё построено
Браузер на телефоне (iOS и Android) НЕ может получить список Wi-Fi сетей и RSSI — закрыто ОС.
- Полную матрицу «комната × все точки» снимает **ноутбук** (или Android через Termux:API).
- Телефон даёт **взгляд клиента**: текущая точка (BSSID), её RSSI/канал, моменты роуминга, задержка/потери.

## Этапы

### Этап 1 — точный расчёт (только код, без телефона)  · команда: «запуск 1»
1. **Общий подбор мощностей.** Модель: прогноз RSSI = замер + (новая мощность − текущая). Перебор/координатный спуск по всем
   точкам сразу (шаг 1 dB, предел 2–10 точек). Цель по приоритету: (а) все комнаты ≥ −67 dBm у основной точки,
   (б) соседняя точка в чужой комнате ≥ 8 dB тише, (в) минимум суммарной мощности.
2. **Прогноз «после»**: в отчёте вторая матрица — как станет с рекомендованными значениями, с отметками исправленных мест.
3. **Поправка клиента**: настройка «клиент слышит хуже ноутбука на N dB» (по умолчанию 6); весь расчёт ведётся
   в «телефонных» dBm. После этапа 3 поправка вычисляется сама.
4. **Потолок по симметрии связи**: 5 ГГц ≤ 20 dBm, 2.4 ГГц ≤ 17 dBm (настраивается), 2.4 на 3–6 dB ниже 5 ГГц той же точки.
5. **Шум**: изменения < 2 dB не предлагать; подсказка «2 замера на комнату (центр + у двери)».
6. Если текущая мощность точки не указана — подбор в относительных dB с пометкой.

### Этап 2 — переходы и проверочный обход (ноутбук)  · команда: «запуск 2»
1. Тип замера: **комната / переход** («Кухня ↔ Холл»). Для перехода отдельная проверка роуминга:
   обе точки −62…−72 и разница ≤ 6 dB → «роуминг пройдёт», иначе — что поправить.
2. **Проверочный обход**: после внесения значений в Omada — новая серия замеров с пометкой «после»;
   сравнение было/стало по каждой комнате и переходу (лучше/хуже/дыра закрыта).
3. Версии плана: «исходный», «после правок N» — откат и сравнение.

### Этап 3 — телефон по ссылке  · команда: «запуск 3»
1. NetKnife поднимает мини-веб-сервер в локальной сети (порт по выбору, случайный токен в ссылке, только LAN),
   показывает **QR-код**. Брандмауэр Windows один раз спросит разрешение.
2. Страница на телефоне (тёмная, крупные кнопки, работает в любом браузере):
   - поле «где я» + кнопки «Комната» / «Переход» → замер пишется в тот же план объекта;
   - **живой тест качества**: задержка, джиттер, потери до NetKnife каждые 0.5 с; провалы отмечаются на маршруте;
   - история маршрута: комната → точка → сигнал.
3. **iPhone**: ссылка на готовую «Быструю команду» (iOS 17+, «Get Network Details»: BSSID, RSSI, канал текущей точки),
   страница вызывает её одной кнопкой. Видно, к какой точке реально прилип телефон и когда переключился.
4. **Android**: инструкция Termux + Termux:API, одна команда — телефон шлёт полный скан (`termux-wifi-scaninfo`):
   Android снимает матрицу наравне с ноутбуком.
5. **Автокалибровка**: в комнатах, где есть и замер ноутбука, и телефона, вычисляется реальная разница — поправка клиента
   из этапа 1 становится измеренной, а не взятой «по умолчанию».

### Этап 4 — отчёт  · команда: «запуск 4»
1. Отчёт объекта (HTML, можно отдать заказчику/монтажнику): матрицы до/после, план мощностей и каналов,
   переходы, итоги проверочного обхода, лист для Omada.
2. «Совет ИИ» получает уже прогноз и данные телефона — проверяет итоговый план, а не сырые цифры.

## Чего НЕ делаем
- Подключение к контроллеру OC200 / Omada API и автозапись настроек — нет (см. память, классификатор).
- Правка бэкапа .cfg контроллера — нет (зашифрован, восстановление заменяет весь контроллер).

## Нужно решить до этапа 3
- Какие телефоны в работе: iPhone, Android или оба (от этого зависит, что делать первым).
- Порт веб-сервера (по умолчанию 8765) и можно ли разрешить его в брандмауэре на этом ПК.

## Детальная схема (готова к запуску, только ноутбук)

**Оптимизатор (этап 1)** — C# через Add-Type (перебор в PowerShell слишком медленный).
- Вход: матрица «строка (комната/переход) × точка», уже в «телефонных» dBm = замер ноутбука − поправка клиента.
- Переменные: изменение мощности d каждой точки; пределы: текущая известна → [3 − текущая, потолок − текущая];
  не известна → [−12, +3] с пометкой «относительно».
- Штраф: 100 × недобор до −67 у лучшей точки строки; 20 × превышение соседа над (лучшая − 8 dB) в комнатах;
  в переходах вместо этого 30 × если вторая точка слабее −78 (роумиться некуда); +1 за каждый dB мощности, +0.3 за |d|.
- Поиск: координатный спуск, шаг 1 dB, два старта (0 и «всем −6»), берётся лучший. Затем |d| < 2 → 0.
- Порядок: сначала 5 ГГц, потом 2.4 ГГц с потолком min(потолок 2.4, итог 5 ГГц − 3).
- Каналы считаются по матрице ПОСЛЕ правки мощностей.

**Отчёт:** матрица «сейчас» и «прогноз» (глазами телефона), отметки «дыра закрыта / стало хуже», таблица точек:
канал, ширина, мощность сейчас → рекомендуемая, зона, примечание.

**Этап 2:** у замера тип «комната / переход» (переключатель у поля); серия замеров («Исходная», «После правок 1…»,
выбор + новая). Расчёт — по текущей серии. «Сравнить серии» — первая против текущей: лучший сигнал в каждой строке
было/стало, Δ, смена основной точки, итог по переходам.

**Этап 4:** «HTML-отчёт» — файл в папке объекта, открывается в браузере: шапка объекта, матрицы до/после,
таблица точек, переходы, сравнение серий, роуминг Omada. «Совет ИИ» получает прогноз и сравнение.

**Новые поля на странице:** поправка клиента (dB, по умолч. 6), потолок 5 ГГц (20), потолок 2.4 ГГц (17),
серия, переключатель «переход»; кнопки «Сравнить серии», «HTML-отчёт».
